# v2.0.1 focused remediation report

Date: 5 November 2026.

Subsequent update: the [launcher locale remediation report](v2.0.1-launcher-locale-remediation-report.md) records the additional environment-preservation correction and current verification totals.

Scope: The four findings from the independent review of the v2.0.1 implementation. Each finding was confirmed against the actual source before correction. The final implementation specification remains unchanged; the user's subsequent requirement to prevent unrelated termination, including uncertain process identity, governs the native test safeguard.

Status: **All four findings remediated and locally verified on Linux.** Application version remains 2.0.1. Nothing was committed, pushed, published, or released. Windows/macOS native verification and the configured CI matrix remain pending.

## Findings, root causes, and targeted corrections

| Finding | Confirmation and root cause | Correction |
| --- | --- | --- |
| Editor/browser lifetime | Both backends called `runCheckedCommand` without launcher-specific options. Its default 15-second timeout could terminate a foreground editor or waiting launcher. | Browser/editor launch calls explicitly use `timeoutMs: 0`. The checked runner, discovery deadlines, liveness bounds, stop-command bounds, and one-second escalation interval are unchanged. |
| Native smoke ownership | Ownership was checked against an earlier snapshot, but the subsequent port-based CLI stop could select a replacement PID. Cleanup also used a numeric-PID signal through `child.kill`. | The native stop boundary now intercepts every Unix `kill` and Windows `Stop-Process` request. It permits only an authenticated request to the test's original spawned fixture over its existing IPC channel. Unknown identity, changed/exited/disconnected processes, wrong PIDs, and IPC errors refuse the request without an external stop fallback. Cleanup disconnects the owned channel; the fixture exits itself. |
| Older action overwrites newer failure | TUI action completions and rejections unconditionally updated one feedback state, regardless of action start order. | A monotonically increasing action sequence gates feedback publication. Older success or failure cannot replace a newer action's feedback. Completed stop actions still request a refresh even when their feedback is superseded. |
| Validation warnings disappear | `validateTarget` returned only a row from its snapshot. The interactive service did not forward that snapshot's warnings to the TUI. | An optional diagnostic callback forwards warnings through exact-target validation for browser, editor, and stop actions. The TUI displays action warnings separately from action feedback, deduplicates them with snapshot warnings, ignores callbacks after unmount, and clears action warnings after a successful refresh. |

Production changes are limited to the two platform launcher methods, scoped diagnostic forwarding in `src/ports.ts`, and TUI feedback/warning state. No dependencies, new commands, JSON fields, general cache policy, or production process-identity architecture were introduced.

## Native process-ownership safeguard

The native test uses a capability tied to the spawned child, rather than treating an earlier PID lookup as permission to signal a later process:

1. The parent captures the spawn-created child handle and PID and creates a random per-fixture token.
2. Readiness must arrive on that child's IPC channel with the matching token and PID. Missing/invalid PIDs or tokens cannot establish stop authority.
3. At every stop request, the guard checks the requested PID against the captured PID, confirms that the same channel remains connected, and checks exit/signal state. Exit, disconnect, error, and send failures invalidate authority.
4. A permitted request is delivered only through that channel. The fixture checks the token and its own `process.pid`, then applies SIGTERM or SIGKILL **to itself**. A recycled PID cannot redirect that channel to another process.
5. Refused/unknown cases never fall back to numeric-PID signaling or an external stop command. Cleanup closes the pipe created for the fixture; the fixture's disconnect handler exits itself. It does not call `child.kill`.
6. Read-only native discovery is allowed through the test runner. Unrecognized commands, malformed stop requests, and PowerShell query strings with appended commands are rejected. Whole PowerShell query forms are matched, so an accepted prefix alone does not grant execution authority.

The sender cannot stop a different process merely because it now owns the selected port. A regression reproduces exactly that sequence: the original snapshot contains the owned PID, a replacement PID appears, and the production port-based stop path is refused at the actual stop boundary with no signal request forwarded.

This protection belongs to the test harness. The production tool's documented PID-reuse and validation-to-signal limitations remain outside this remediation's scope.

### Deliberate native verification adjustment

The native stop exercise now invokes the actual production command handler and platform backend with a test-only signal runner. Native enumeration, metadata collection, target validation, one-second stop flow, liveness, and listener release are real. Linux verification confirmed that the fixture exited with SIGTERM and that the separate owned sentinel retained its live IPC identity.

The test does **not** execute an unrestricted built CLI `kill` command against a host port. The built executable is still exercised for native list/check behavior. Positive built-CLI termination coverage was added using fake signal executables, which never terminate host processes. This test-boundary adjustment is necessary to satisfy the user's stronger ownership guarantee without changing production commands or adding production test switches.

The native test command now loads the existing `tsx` development dependency so it can inject the safe runner into the production command handler. No dependency was added. The test-only PowerShell allowlist deliberately fails closed if production query forms change; its regression test exercises all current backend read-only queries.

## Regression coverage added

- Launcher options are checked for both editors and browser launchers on both backends; stop commands retain their 15-second bound.
- A harmless configured Node editor stub remains open for 16 seconds and exits successfully, beyond the former automatic timeout. No real editor or browser is launched.
- A delayed older browser success or rejection cannot erase a newer stop failure in the rendered TUI.
- Real `PortService` validation warnings reach the rendered TUI for browser, editor, and stop actions, including a subsequent launch failure. A healthy post-stop refresh clears the transient action warning.
- Native ownership tests cover authenticated requests, absent readiness, wrong tokens/PIDs, missing or malformed spawn identity, invalid authentication tokens, disconnection, exit, PID reuse, unsupported signals, synchronous/asynchronous IPC failure, and cleanup without a stop fallback.
- Native runner tests verify interception of both Unix signal forms and both Windows stop forms, refusal of unknown commands, rejection of appended PowerShell commands, and read-only query compatibility.
- A port-replacement regression verifies that a newly selected replacement PID is never passed to an OS stop command or to the owned fixture's channel.
- The positive built-CLI stop integration case records fake signal-executable invocation while leaving host processes untouched.
