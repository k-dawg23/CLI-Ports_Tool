## Actual native host

Final runner: Windows 10.0.26100, win-x64, Node v24.22.2. Build SDK: .NET 10.0.403/MSBuild 18.9.15; helper target/runtime: .NET 8/8.0.33. Complete SDK/runtime information is retained in `dotnet-environment.txt`; runner setup/image details are in `jobs.log`.

The helper creates synchronous input/output pipe pairs solely as the documented transport to `CreatePseudoConsole`; it does not attach ordinary redirected pipes as the Node child's terminal. It passes the genuine HPCON through `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` in `STARTUPINFOEX`, then calls `CreateProcessW`. Each hosted child is created suspended, assigned by its exact process handle to an owned Windows job, then resumed. Output is drained on a separate thread, including during `ClosePseudoConsole`. This follows the [Microsoft ConPTY API/lifetime guidance](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session).

Viewport: 160 columns by 60 rows. The helper emits native creation HRESULT, child identity, exact command array, raw output bytes, child exit and cleanup results. Input events are timestamped and retained. The actual CLI preloader records native `isTTY` values and calls through to the real `setRawMode`; neither property is spoofed.

Example commands, with the exact expanded runner paths retained in `experiment.json` and workflow logs:

```text
dotnet --info
dotnet build scripts/conpty/ConPtyHost.csproj -c Release -o <fresh-evidence-directory>/host
node scripts/conpty/experiment.mjs --cli
dotnet <fresh-evidence-directory>/host/ConPtyHost.dll <node.exe> <keyboard-probe.cjs>
dotnet <fresh-evidence-directory>/host/ConPtyHost.dll <node.exe> --require <observe-cli.cjs> <repository>/dist/cli.js
```

The first failure was a helper initialization defect. Windows duplicated the host's redirected standard handles into the child despite disabled handle inheritance. The probe reported no terminal/raw-mode support through the host protocol pipe, while the genuine ConPTY output contained only console control sequences. Thus the initial attempt correctly failed rather than claiming a pipe-based terminal pass.

The narrow correction sets `STARTF_USESTDHANDLES` with null standard handles, allowing Windows to connect the child to the pseudoconsole instead of duplicating redirected host handles. This case and correction are described in the [Microsoft Terminal maintainer discussion](https://github.com/microsoft/terminal/discussions/15814). Additional assertions reject unexpected child output bypassing the ConPTY channel. The successful rerun demonstrated that the issue was the helper setup, not ConPTY unsuitability.

Run 42201698269's overall conclusion was failure because the macOS native artifact upload exhausted five GitHub ArtifactService timeout retries. Its Windows job, including Stage 1, passed and its ConPTY artifact was downloaded successfully. No application correction was made for that upload failure. The final matrix rerun completed successfully on all platforms, including artifact uploads.

## Stage 2 inspected evidence

The final artifact records the actual compiled entry point `dist/cli.js`, not an imported TUI component or mocked terminal renderer. Native discovery remained production PowerShell-backed execution; nine successful Get-NetTCPConnection query exits were observed. The preload only logs those calls and forwards them unchanged.

Ink normally suppresses interactive redraws under CI. The hosted CLI alone receives the explicit environment override `CI=false` to exercise its normal interactive renderer; actual OS TTY/raw-mode detection remains untouched. Other recorded launch environment values are explicit test markers, not claims about the runner's default locale.

Observed session:

1. Actual CLI stdin/stdout TTY values and raw-mode capability were true, with a 160×60 terminal. A real raw-mode call succeeded and the viewport showed `ports v2.0.1`; no non-TTY fallback appeared.
2. Native input `/`, `conpty-owned`, Enter filtered to two authenticated owned listeners. Down Arrow selected PID **5532**, port **60895**; the other fixture was PID 968, port 60894. The selected-details panel and highlighted row agreed.
3. `r` was recorded by the child's real terminal input observer. A new native discovery query started 128 ms later, before the next automatic timer callback. The manual-refresh frame retained PID 5532/60895 and showed `Refreshing...`.
4. Two further real 3-second timer opportunities and successful native queries were required with no intervening keyboard input. Five timer callbacks were recorded over the entire session. The automatic-refresh frame retained the same selected identity.
5. A third authenticated owned listener, PID 5264/port 60897, appeared in an actual rendered frame and disappeared after its own IPC disconnect. Selection stayed PID 5532/60895 in both frames.
6. `s` changed the rendered mode from `[port asc]` to `[memory desc]`; selection stayed PID 5532/60895. This native run verifies the sort switch and identity retention, but does not claim every possible memory-rank permutation; deterministic reorder regression coverage remains separate.
7. `e` ran the harmless configured Node launcher. It received exactly two arguments: `editor argument with spaces` and the actual directory ending `conpty\\owned project with spaces`. The fixture executable is deliberately located there so real Windows process metadata/project discovery supplies the spaced directory.
8. `o` passed fresh native target validation, then the exact generated `Start-Process "http://localhost:60895"` launch was redirected to a harmless child probe. No actual browser was opened; real discovery and shell lookup were not replaced. The probe received the single URL argument `http://localhost:60895`.
9. Both launcher children received unchanged `LC_ALL=en_GB.UTF-8`, `LANG=en_GB.UTF-8`, `LC_MESSAGES=de_DE.UTF-8`, `LANGUAGE=en:de` and `PORTS_CONPTY_MARKER=inherited marker with spaces`.
10. `q` reached native terminal input. The compiled CLI restored raw mode to false and exited with status 0. The helper also exited 0 and recorded child exit, closed HPCON, drained output and closed owned handles/job. All three loopback fixture exit events were awaited following owned IPC disconnect.

The inspected artifact contains 37,529 characters of raw compiled-CLI terminal output, seven decoded checkpoint frames, keyboard events, read-only observations and launcher logs. The decoder applies cursor positioning/clearing; it does not merely search all historical output for matching stale text. Raw output and original base64 chunks remain available for independent review.

No `K` input or unrestricted application termination shortcut was sent. The test preload additionally rejects stop commands. Fixture cleanup reuses the accepted spawn-owned IPC guard; unknown ownership never triggers PID-based signals. The helper's failure cleanup can terminate only its assigned job through its owned kernel handle. Closing a job/session is cleanup of its attached owned children, not a substitute for verifying product process-termination behavior.

## Limitations and future reuse

This approach is viable for future Windows CLI projects without physical-machine access: the native host and harmless Stage 1 probe can be reused independently of this application. No production dependency or terminal-testing framework was added. Keep the redirected-handle correction, concurrent output drain, explicit stage gate, exact child/job handle ownership and per-run artifact separation.

Reuse is conditional on adapting the application scenario and independently qualifying the terminal protocol. The viewport decoder is intentionally small, fixed-size and single-width-character oriented; it is not a general VT/Unicode terminal emulator. It rejects unsupported CSI operations. Other terminal dimensions, resize behavior, Unicode display widths, mouse/paste/focus input, additional Windows versions/architectures and installed GUI applications were not qualified. No repeated-run reliability or broad performance guarantee is established by this experiment. A future hardening pass could bound fixture-readiness failures more explicitly, record descendant job accounting and avoid uploading fixture runtime binaries; none is needed to reinterpret the observed passing session.

The existing final release plan still has outstanding Linux/macOS native terminal/shortcut verification, actual backend-selected Windows PowerShell executable/version recording, and an explicit resolution of the previously recorded termination-evidence boundary. This experiment does not change the release specification or waive those checks. **AC-12 remains pending; do not merge, tag or publish v2.0.1 on this report alone.**
