# v2.0.2 test capture remediation and local results

Verification date: 2026-11-07. Host: Linux 7.0.0-42-generic, Node v24.21.0. Evidence is retained in [attempt 1](v2.0.2-test-capture-2026-11-07-attempt-1/). No commit, push, release, or CI dispatch was performed.

## Changes

The failing child fixtures previously used Node stream writes, which this environment initializes as no-op Writable streams when their descriptors are socket-backed pipes. Direct descriptor writes work. The foundation diagnostic fixtures and launcher environment JSON fixture now use `fs.writeSync`, preserving their command-result, stderr, locale, timeout, and cancellation assertions.

`scripts/stdio-preflight.mjs` separately checks actual asynchronous Node stdout/stderr through Execa pipes. Default integration execution requires it. Failure identifies the missing stream output explicitly rather than reaching misleading JSON parse assertions. GitHub Actions now runs this check before the unit suite on every existing matrix job.

Integration tests use a test-only capture helper. The default path retains Execa piped capture. Explicit `npm run test:integration -- --file-capture` redirects the actual built CLI stdout/stderr to temporary regular files, reads both separately after process close, and retains all existing integration assertions. Owned CLI execution has a 35-second timeout and temporary files are cleaned up. Both the runner and helper reject file capture when `CI=true`. This is local redirected-output verification, not pipe acceptance. Application source, output handling, dependencies, action targeting, and the four-job CI matrix were not changed by this remediation.

## Host-terminal follow-up: inherited color environment

The user's normal Ubuntu terminal passed the pipe preflight. Its integration run passed two scenario groups but failed the clean-stderr assertion because inherited `FORCE_COLOR` conflicted with the fixture's explicit `NO_COLOR`, causing Node to emit a startup warning. This confirms pipe capture works in that host terminal; it does not make the earlier restricted-environment run a pass.

The integration fixture now removes all case variants of `FORCE_COLOR` from its copied child environment, preserving its explicit no-color policy and leaving the parent unchanged. A new built-CLI regression injects conflicting inherited values, verifies their removal and parent preservation, and requires valid JSON with empty stderr.

Verification: `FORCE_COLOR=1 npm run test:integration -- --file-capture` passed the existing integration groups; the new color-isolation regression passed separately in file-capture mode. `git diff --check` passed. The outer test runner can still print its own inherited-color warning before fixture setup; the fixture's child CLI no longer emits it. A normal piped integration rerun in the user's host terminal remains outstanding after this correction.

### Follow-up correction: Execa environment merging

The user's subsequent piped run still failed the two clean-stderr assertions. The fixture environment was sanitized, but the piped test helper used Execa's default `extendEnv: true`, restoring the removed parent `FORCE_COLOR`. File capture used `spawn` with the exact environment and therefore did not expose this difference. The earlier file-mode result was insufficient to verify the piped fix.

The piped capture helper now explicitly sets `extendEnv: false`, matching file mode. A new `cli-capture.test.ts` regression exercises that actual piped helper with parent-only markers and `FORCE_COLOR`, an exact child environment containing `NO_COLOR`, and synchronous fixture JSON output. It verifies absent parent variables, empty stderr, and an unchanged parent environment without depending on this environment's broken asynchronous stream initialization.

Verification after this correction: all 13 unit test files passed; all four integration scenario groups passed in file-capture mode; typecheck and `git diff --check` passed. The new exact-environment piped regression also passed directly. Normal piped integration must be rerun on the user's host terminal; Windows/macOS execution remains assigned to the existing GitHub Actions matrix. No production command runner or application environment behavior was changed.
