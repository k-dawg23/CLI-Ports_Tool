### Why the executable identity is reliable

A Windows-only native check invokes the production `WindowsPortBackend.getListeningPorts` with a test-only observing command boundary. Lookup requests are forwarded to the unchanged production command runner and recorded. The backend itself chooses the shell; the observer does not select an alternative installation.

For the selected shell's actual native listener query, the observer preserves the original argv prefix, command options and discovery expression. It appends file-only metadata output after that expression. **Inside that same process**, metadata reads `[System.Diagnostics.Process]::GetCurrentProcess().MainModule.FileName`, `$PSVersionTable.PSVersion`, edition and `$PID`. The original discovery JSON remains stdout; the identity record goes to a uniquely named UTF-8 file under the fresh evidence directory. Its nonce is validated before accepting it.

The unchanged backend parses and validates the native result, which contains the authenticated owned target PID/port. The evidence retains the original command, instrumented command, native stdout/stderr/status, lookup result, nonce-bound identity and found target.

The test then launches a separate version query through the **absolute executable path reported by that discovery process**. It verifies exit 0 and requires the query to report the same executable, version and edition. Thus the result is not a version query against an independently chosen shell or an assumption based on the workflow's pwsh host.

The native artifact carries the candidate SHA, run ID, attempt, logical job key, runner, Windows version and Node version. The retained GitHub job results and Windows upload log link that matrix instance to numeric job ID 127886437504 and native artifact 13501571767. Artifact metadata independently associates it with the same run and head SHA.

**RV-07: PASS.** The previously missing backend-selected executable/path/version record is now present, native, tied to successful discovery and reviewable.

### RV-03 signalling boundary

The native smoke harness exercises production stop logic with real enumeration/liveness, but intercepts the OS stop command at the test runner boundary. An authenticated request reaches only its spawn-owned fixture, which signals itself. The fixture exits, its listener disappears and the owned sentinel survives; deterministic regression tests verify command construction and guarded escalation behavior.

It does not execute external kill/Stop-Process directly from the packaged CLI. Under Work's accepted interpretation of section 7.3, that is additional coverage, not a mandatory release gate. The recorded safe termination outcome satisfies RV-03. No safeguards were weakened to obtain this decision, and no unrelated process was terminated.
