# CLI Ports Tool v2.0.1 implementation specification

Status: Final, ready for implementation; this document does not implement the changes.

Target release: **v2.0.1**, replacing **v2.0.0** as the current application version.

Scope: Improvements 1–3 from the repository review: target the selected process correctly, distinguish discovery failures from empty results, and validate port arguments strictly.

Refresh coordination, bounded collection, and regression coverage support these three fixes; they do not introduce a general performance or cache redesign. Intentional compatibility changes are limited to strict port parsing, PID-specific TUI actions and selection, explicit discovery errors/stale state, diagnostics on stderr, and the guarded termination outcomes defined below. Existing commands and successful JSON output remain compatible.

## 1. Problem statement

### 1.1 Actions can affect a different process from the selected row

The TUI presents rows identified by PID and port, but its action helpers receive only a port. Each helper discovers listeners again and selects the first process on that port. When multiple processes share a port, pressing `K` can stop a process other than the displayed selection, and pressing `e` can open another process's directory. Index-based selection can also move to another process when refreshes or sorting reorder the rows.

### 1.2 Discovery failure can look like an empty machine

Some external-command failures are ignored or converted to missing output. In particular, Windows discovery can return an empty array when PowerShell is missing, a query fails, or its output cannot be parsed. Unix discovery ignores command exit status and stderr. Consequently, `list` can report no listeners and `check` can report a port as free without a successful discovery operation.

The TUI retains rows when an exception reaches it, but it does not identify those rows as stale. Errors swallowed by the backend instead replace the rows with an apparently successful empty snapshot.

### 1.3 Invalid port strings can become valid targets

The shared CLI argument parser uses `Number.parseInt`. Inputs such as `3000abc` and `3000.5` become port 3000, and `3e3` becomes port 3. A malformed argument can therefore inspect or stop an unintended listener.

## 2. Findings

These findings describe the inspected v2.0.0 source. Static inspection established the control-flow defects; cross-platform runtime reproduction has not yet been completed.

| Component | Established behavior | Implication |
| --- | --- | --- |
| `src/tui.tsx` | `K`, `o`, and `e` pass only `currentSelected.port`; selection is stored as `selectedIndex`. | Action targeting and selection do not preserve the selected listener's identity. |
| `src/ports.ts` | `getPortDetails` calls `getListeningPorts` and uses `.find` by port. Kill and editor helpers use that result. | A different PID sharing the selected port can be chosen. |
| `src/ports.ts` | Listener rows are enriched and sorted by port; multiple PIDs on the same port are supported. | Shared-port handling is an existing supported data case, not a hypothetical model extension. |
| `src/system.ts` | `runCommand` uses `reject: false`, discards stderr, and returns only stdout. `runCommandOrUndefined` suppresses thrown failures. | Callers cannot reliably distinguish successful absence from failed collection. |
| `src/backends/unix.ts` | Listener collection parses `lsof` stdout without checking exit status. | A failed query can become an empty result. A missing executable can also throw. |
| `src/backends/windows.ts` | Missing shell, absent output, and JSON parsing errors become `undefined`; missing listeners normalize to `[]`. | Discovery failures can be reported as no listeners. |
| `src/tui.tsx` | Automatic and manual refreshes have duplicated logic and may overlap; ordinary status updates can clear error messages. | Failure state and action feedback can be overwritten or applied out of order. |
| `src/cli.tsx` | The no-argument fallback performs discovery outside the command parser's error handler. | Failure handling is inconsistent between the fallback and explicit commands. |
| `src/cli.tsx` | `parsePort` checks the result of `Number.parseInt`, rather than the complete input. | Trailing characters, fractions, and exponent notation are accepted as truncated integers. |
| `package.json` | Build, development, and start scripts exist; no test script or automated test suite was found. | Regression coverage and a repeatable test command must be introduced. |
| Release metadata | Version 2.0.0 appears in package metadata, CLI/TUI constants, and current-release documentation. | Updating only `package.json` would leave conflicting version displays. |

The investigation confirmed the malformed-input conversions and that the build and TypeScript checks passed before implementation. Those checks do not establish correct action targeting or platform discovery behavior.

## 3. Proposed solution

### 3.1 Target actions using the selected PID and port

Introduce an internal listener target containing `{ pid, port }`. TUI actions must capture this target when the key is pressed and retain it throughout the asynchronous operation. Do not resolve a selected row again using only its port.

Required behavior:

1. Keep a port-oriented entry point for `ports kill <port>`, preserving its documented first-discovered-listener behavior. Resolve the CLI target once, then delegate to the same PID-specific action path used by the TUI.
2. Before stopping a captured target, perform fresh listener discovery and require an exact PID/port match. If it is absent, report that the selected listener is no longer available. Do not substitute another PID, even if the port remains occupied.
3. After the existing one-second wait, check process liveness using the three-outcome contract below. If exit is confirmed, report success. If the process is alive, perform fresh PID/port validation before the forced-stop phase. If it no longer listens on the target port, omit the forced stop and report “Listener released; process still running” as an incomplete stop with exit status 1. Unknown liveness or failed discovery must prevent escalation and report that the stop could not be verified. A missing listener alone is not proof that the process exited.
4. For `e`, locate the exact selected PID/port in a fresh successful snapshot and use that row's detected working directory. Freshness here applies to listener enumeration; existing cached metadata remains best effort as described below. Keep the existing missing-directory error and editor precedence.
5. For `o`, validate the selected PID/port, then open the existing `http://localhost:PORT` URL. This opens an endpoint; it cannot choose which process a shared endpoint routes to. Do not claim process-specific browser routing.
6. Disable repeated activation of the same pending action, and preserve action failure messages independently of routine refresh status. A successful subsequent action may replace the preceding action result.
7. If discovery fails during validation, perform no new kill, browser, or editor operation and show the discovery error.

The backend stop operation must receive the expected target or a validation callback so the forced phase cannot bypass this contract. Continue using direct argument arrays for executable invocation; do not introduce shell interpolation of user input.

Replace the boolean liveness contract with `alive`, `exited`, or `unknown`, retaining the reason for an unknown result. Only an OS result that establishes absence may produce `exited`. A permission-denied probe that establishes existence may produce `alive`; permission denial without that evidence, missing tools, timeout, invalid output, and other query failures produce `unknown`. Do not map every unsuccessful `kill -0` or PowerShell query to process exit.

Termination outcomes apply to both CLI and TUI actions:

| Outcome | Result/message | CLI exit status |
| --- | --- | --- |
| Exit confirmed after the initial stop | Success: process stopped | 0 |
| Process alive and original PID/port still present after the wait | Send the existing forced stop to the captured PID, then perform a bounded liveness check | Determined by that check |
| Exit confirmed after the forced stop | Success: process stopped with forced termination | 0 |
| Process alive but original listener released before escalation | Incomplete: listener released; process still running; no forced stop | 1 |
| Liveness unknown, validation fails, or stop command fails | Failure/unverified result with the reason; no further signal | 1 |
| Forced stop accepted but final liveness check reports alive or unknown | Forced stop requested; process exit not confirmed; no further signal | 1 |

The final liveness check does not add another signal or alter the one-second interval before escalation. These guards intentionally narrow automatic escalation and success reporting; preserve the existing signal sequence whenever escalation is permitted.

Preserve selection by PID/port across successful refreshes and sort changes while that target remains visible. Arrow navigation changes the selected target. Existing filter and search changes may continue resetting to the first visible row. If a selected listener disappears, select the row at its previous visible position, clamped to the available rows; an empty list has no selection. An already-started action keeps its captured target regardless of later UI selection changes.

PID/port revalidation reduces stale-target mistakes but is not an atomic operating-system guarantee: a process can exit or a PID can be reused between validation and signaling, including reuse with the same port. This patch must not describe that race as eliminated. Existing PID-keyed cwd/project caches can also retain stale metadata across undetected PID reuse; fresh enumeration does not guarantee a fresh directory or process-start identity. Stronger process-start identity handling and general cache invalidation remain outside this release's required scope. Keep these limitations explicit in documentation and test the exact PID/port guarantees without claiming stronger identity protection.

### 3.2 Make listener discovery success explicit

Separate required listener enumeration from optional process enrichment. A successful query with no listeners is valid; an unsuccessful query is an error. Missing memory, uptime, cwd, or project information must not discard an otherwise valid listener.

Add a checked command-result path that retains stdout, stderr, exit status, and launch/timeout failures. Use it for required discovery rather than globally changing every best-effort helper. Give each active snapshot collection a 15-second total deadline, starting when it acquires the discovery coordinator. All prerequisite checks, required enumeration, optional subprocesses, and project enrichment share the remaining budget; no subprocess receives more than that remaining time. Queue wait time is separate from this collection deadline. Use configurable/injected deadlines in tests so tests do not wait in real time.

If required enumeration fails or exceeds the deadline, fail the snapshot. If enumeration has succeeded but optional enrichment cannot finish within the remaining budget, return the known listener rows with unavailable-field fallbacks and a concise warning. Cancel outstanding subprocesses and ignore unfinished optional work; late completion must not publish cache or UI updates. Apply a separate 15-second maximum to each liveness probe and stop-command invocation so an action cannot hang indefinitely in verification or signaling. This does not change the existing one-second wait before escalation.

Normalize required-discovery failures into an internal typed error with a code, platform/backend context, and an actionable message. At minimum, distinguish missing prerequisite, command failure, invalid output, and timeout. Keep these types internal; do not add fields to successful JSON output.

Unix requirements:

- Check `lsof` completion status and preserve diagnostics.
- Treat exit status 0 with a recognized empty/header-only result as a successful empty collection.
- Classify status 1 with empty stdout and stderr as the expected no-match result for the supported invocation. This is an implementation rule requiring native Linux and macOS verification under section 7.3, not a platform behavior already established by the investigation. Do not treat other nonzero outcomes as empty merely because stdout is blank.
- Detect nonempty output that cannot be recognized as the expected listener format. Fail rather than silently discarding every malformed record or returning a misleading partial snapshot. Prefer an explicitly parsed `lsof` field format if needed to make this distinction reliable.
- Surface a missing `lsof` with an installation/PATH hint. Treat unavailable optional `ps` metadata as incomplete details, not zero listeners.

Windows requirements:

- Report missing `powershell`/`pwsh` explicitly.
- Make `Get-NetTCPConnection` errors terminate the required enumeration operation and produce a failed command result. Do not allow a failed query to serialize a success-shaped empty payload.
- Require a valid JSON snapshot with a `Listeners` array, including `[]` for a successful empty result. Reject absent, malformed, or invalid listener data rather than normalizing it to `[]`.
- Validate listener PID/port values as integers in their applicable OS ranges. Retain legitimate system-owned listener records; this validation must not silently drop them.
- Keep process-statistics and CIM enrichment best effort. A process disappearing during enrichment or inaccessible optional metadata must not invalidate successful listener enumeration.

For both backends, preserve listener rows when only metadata is unavailable. Known broad metadata failures, such as missing `ps` or an enrichment deadline, must produce a concise warning rather than a warning for every PID. Ordinary per-process disappearance need not produce noisy warnings. Carry warnings separately from the process array in an internal snapshot structure; display them in the TUI and on CLI stderr without changing successful JSON.

Neither a successful query nor this patch guarantees visibility of listeners hidden by OS permissions. User-facing free/empty results remain subject to that documented visibility limit.

### 3.3 Apply a consistent CLI output and exit-status contract

Wrap both the default non-TTY path and Commander execution in one top-level error boundary. Diagnostics, including the non-TTY fallback notice, go to stderr. A fatal discovery failure exits with status 1 and must not print a success table, `[]`, or a free-port message.

| Invocation/outcome | stdout | stderr | Exit status |
| --- | --- | --- | --- |
| `list` succeeds | Existing table or genuine empty-list message | Optional enrichment warning | 0 |
| `list --json` succeeds | Existing JSON array, including genuine `[]` | Optional enrichment warning | 0 |
| `check` succeeds with no matching listener | Existing free-port message | Optional enrichment warning | 0 |
| Any discovery-dependent command fails discovery | No success payload | Actionable discovery error | 1 |
| `kill` finds no listener or fails its action | No success payload | Failure/free-port diagnostic | 1 |
| `kill` releases the listener but leaves the process alive, or cannot verify exit | No success payload | Incomplete/unverified stop diagnostic from section 3.1 | 1 |
| `kill` succeeds | Existing success message | Optional enrichment warning | 0 |
| `check` or `kill` receives an invalid port | Empty | Validation error and supported range | 1 |

`--help` and `--version` must work without requiring platform discovery tools. Successful JSON retains its current array shape and fields. Moving failure diagnostics to stderr is an intentional correction and must be documented.

### 3.4 Retain and label stale TUI data

Use one discovery coordinator shared by refreshes and action validation. Serialize the full enumeration-and-enrichment snapshot operation, including backend cache access/publication; permit only one such operation in flight. Return a snapshot whose listener rows and metadata cannot be mutated by later collections. Action validation must start a new collection after its request is queued; it must not reuse an earlier in-flight or cached snapshot as fresh validation.

Use one TUI refresh path for startup, timer, manual refresh, and post-action refresh. Preserve the three-second automatic refresh interval and coalesce refresh requests made during a collection into at most one follow-up refresh. Serialize action-validation requests through the same discovery coordinator, service them before pending routine refreshes, and retain each captured target. Release the discovery coordinator before signaling or waiting for termination; subsequent escalation validation reacquires it rather than recursively holding the coordinator. Ignore late collection and action UI updates after unmount.

This coordination is limited to preventing overlapping collection/cache updates for the specified fixes. It does not require metadata batching, broad cache invalidation, or new refresh settings.

Track whether a successful snapshot exists, its completion time, the current discovery error, and action feedback separately.

- On refresh failure after a success, retain the last successful rows and selection and visibly label them stale with the last successful refresh time and current error.
- On initial discovery failure, show an unavailable/error state. Do not show “No ports match” or imply there are no listeners.
- On the next successful discovery, replace the rows, update the timestamp, and clear the discovery error/stale state. A genuine successful empty snapshot clears old rows.
- Filter, search, and sort controls must not clear an unresolved discovery error or make stale data appear fresh.
- Actions from stale rows must still perform fresh exact-target validation; never act solely on stale data.
- Display action failures as failures. A successful refresh after a failed kill must not turn that action failure into an ordinary success status.

### 3.5 Validate the complete port argument

Extract a pure parser/validator for reuse and direct tests. Accept ASCII decimal digit strings only, then convert with `Number` and require an integer in the inclusive range 1–65535. Leading zeros are accepted as decimal: `003000` means 3000. Do not trim whitespace or accept signs, decimal points, prefixes, separators, suffixes, or exponent notation.

Use the same validator for both `check` and `kill`, preferably through Commander's `InvalidArgumentError`. Validation must complete before constructing/querying a backend or initiating any side effect.

Examples:

| Input | Result |
| --- | --- |
| `1`, `3000`, `65535`, `003000` | Accepted; converted to the intended decimal port |
| `0`, `65536`, `999999999999999999999` | Rejected as out of range |
| `3000abc`, `3000.5`, `3e3`, `0xBB8`, `+3000`, `-1` | Rejected |
| Empty string, quoted whitespace, `" 3000"`, `"3000 "`, non-ASCII digits | Rejected |

The implemented application version **must change from v2.0.0 to v2.0.1**. Stored package version values use `2.0.1` without the `v` prefix.

Update:

- `APP_VERSION` in `src/cli.tsx` and `src/tui.tsx`, or replace them with one shared build-compatible version source. Both user-visible displays must agree with package metadata.
- Current-release labels and examples in `README.md`, `USER_MANUAL.md`, and `index.html`.
- Add a v2.0.1 entry at the top of `PROJECT_HISTORY.md`, describing these fixes. Use the actual release date when released; do not invent a completed release date in advance.
- Correct documentation stating that TUI actions may target another row's PID, describing swallowed discovery failures as expected behavior, or accepting truncated port input.

Preserve historical v2.0.0 release notes and accurate statements that cross-platform support began in v2.0.0. Do not replace dependency versions containing `2.0.0` in the lockfile.

## 5. Implementation constraints

- Keep macOS, Linux, and Windows support and the current Node engine requirement.
- Preserve the commands `ports`, `list`, `list --json`, `check <port>`, and `kill <port>` and their successful output semantics, except for the specified fixes.
- Keep the existing JSON field names, types, null fallbacks, array structure, ordering by port, and PID/port deduplication.
- Keep TCP-only discovery, current framework detection, project lookup behavior, and editor precedence.
- Keep TUI shortcuts, filter modes, search semantics, sort modes, and three-second automatic refresh behavior. Selection identity and error persistence change as specified.
- Keep Unix SIGTERM followed by the existing one-second wait and conditional SIGKILL. Keep Windows Stop-Process followed by the existing one-second wait and conditional forced stop. The explicit exceptions are the validation/liveness guards and incomplete-stop outcomes in section 3.1: do not escalate after the listener is released or verification fails, and do not claim an unverified process exit. Do not add other signals, configurable termination policies, confirmation prompts, or automatic privilege elevation.
- Stopping a process still affects all its ports. The CLI still stops only the first discovered listener on the requested port; bulk termination and new PID command flags are out of scope.
- Do not introduce new runtime dependencies unless an existing capability cannot satisfy a requirement. Prefer the existing `tsx` tool and Node's test runner, with a development-only TUI testing helper if needed.
- Do not broaden this patch into listening-address output, CLI filtering options, layout redesign, framework improvements, general cache invalidation, or a `ports doctor` command. The diagnostic command was an optional suggestion and is deferred.
- Tests must use mocked backends or processes they own. Never terminate unrelated host processes or launch the user's real browser/editor during automated tests.

## 7. Testing requirements

### 7.1 Test infrastructure and required commands

Add `npm test` for the regression suite and `npm run typecheck` for `tsc --noEmit`. Prefer Node's test runner through the already installed `tsx` loader. Ensure test-file discovery works on Windows without relying on Unix-only shell expansion. Extract pure selection/validation helpers and inject backend/command execution where necessary so tests can exercise behavior without host dependencies.

The release checks are:

```text
npm ci
npm run typecheck
npm test
npm run build
npm run test:integration
node dist/cli.js --help
node dist/cli.js --version
```

Add `npm run test:integration` to execute the built entry point and verify error handling, streams, and packaging after the build. Keep `npm test` independent of pre-existing build artifacts. All required checks must pass before release.

### 7.3 Platform checks

Run type checking, automated tests, build, and built CLI integration checks in a CI matrix on Linux, macOS, and Windows using a supported Node 24 release at or above 24.11.0. Also exercise the declared minimum Node 22.18.0 on at least one CI platform. Fixture tests must cover both backends on every platform, regardless of the host OS.

On each supported OS, perform native smoke checks with a temporary loopback TCP server owned by the test:

1. Confirm it appears in `list`, `list --json`, and `check`.
2. Confirm normal termination targets only that owned process and the listener disappears.
3. Confirm a genuine unused port is reported free after successful enumeration.
4. Confirm the TUI starts, refreshes, preserves selection, and exits normally in a real terminal.
5. Confirm browser/editor shortcuts with harmless test executables or a command-runner stub, including paths containing spaces.

On Linux and macOS, capture native `lsof` fixtures for the actual flags/output format used by the implementation: valid listeners, IPv4/IPv6 records, warnings/errors, and a controlled no-match query. Record stdout, stderr, exit status, and tool/platform version. The controlled no-match query may add a port or process selector to obtain no matches on a machine with unrelated listeners. Verify the empty-result rules in section 3.2 against these fixtures before release. If a supported platform produces a different no-match signature, add only an explicitly verified platform-specific classification and its regression fixture; do not broaden the rule to ignore arbitrary command errors.

Shared-port targeting and forced escalation can use deterministic backend fixtures when native socket-sharing or process behavior differs between operating systems. Native tests must clean up only their own resources. Implement and run all locally available checks without waiting for other platforms, then use CI/native runners for the remaining checks. Record each platform, runtime/tool versions, commands, and pass/fail results; distinguish fixture coverage from native execution. Record unexecuted checks as pending, never passed. All required native checks and the supported Unix no-match classifications must be verified before v2.0.1 release acceptance; a build alone is insufficient evidence.
