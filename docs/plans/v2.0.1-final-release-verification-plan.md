### Termination evidence boundary

The current harness runs production action logic with real discovery/liveness, intercepts the stop command, and requests authenticated fixture self-signalling. This proves native listener disappearance and owned-process exit, while deterministic fixtures verify kill/Stop-Process command construction. It does not prove direct external command execution from the packaged CLI.

Section 7.3 requires safe normal termination and its outcome; it does not separately name an "unrestricted kill command" test. Keep that distinction explicit. The previous verification report lists direct execution as an unresolved coverage gap, so do not silently mark it passed or add unsafe signalling merely to remove that label.

Before closing RV-03, obtain an explicit release-review decision on whether the combined guarded-native and command-fixture evidence satisfies the stated outcome. If direct execution is required, design a test-only native isolation/ownership mechanism, review it first, and execute it on disposable CI environments only when it can prevent an unrelated process from receiving a signal even if identity becomes unknown or changes. Merely checking a PID immediately before kill, passing a nonce once, or having a disposable runner is insufficient to eliminate PID-reuse risk. Abort without signalling on uncertainty. If that guarantee cannot be established, retain the direct-execution gap as pending and seek suitable isolated access; do not bypass the guard. Accepting the existing boundary must be documented as an evidence decision, not represented as a direct-command pass. Any change to an actual specification requirement needs explicit approval.

Shared-port behavior and forced escalation may continue to use deterministic fixtures, as section 7.3 explicitly permits. Do not require new native socket-sharing or forced-kill scenarios to complete this patch.

## Automatable: GitHub Actions work

### A. Retain and complete native command evidence

Use the existing four-job matrix. Capture actual runner OS/image/architecture, Node version and candidate SHA. On Windows, determine the shell selected by the backend's existing `powershell`-then-`pwsh` lookup, record its resolved executable and `$PSVersionTable` using that executable, and record lookup/query results. Do not infer the backend shell from the workflow's default PowerShell host. Do not change shell precedence to simplify testing.

Retain native table/JSON/check, free-port and guarded-termination checks. Retain Unix raw lsof commands, stdout, stderr, statuses and tool versions. Assert each artifact is newly generated, has the expected platform, and belongs to the current run/candidate. Continue uploading from a fresh run/attempt directory; never collect repository-wide historical native files. Upload useful failure records even when the checks fail, without calling them successful evidence.

### B. Add native terminal interaction checks

Linux and macOS can run the built CLI in an OS-backed pseudo-terminal. Python's `pty` module is Unix-only and can provide a small test-only harness; it is not a Windows solution. [Python PTY documentation](https://docs.python.org/3/library/pty.html)

Windows needs a native ConPTY host, for example a small test-only helper based on the documented Windows API. First prove that the runner can host this session and that Node/Ink receives a terminal with working raw input. Do not assume ordinary PowerShell subprocess pipes or Git Bash's terminal behavior provide this. Prefer a narrowly scoped test helper; avoid adding product runtime dependencies or a general terminal framework. [Microsoft ConPTY session documentation](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session)

For each terminal job:

1. Start two authenticated owned loopback fixtures and choose their exact PID/port rows. Use no keyboard kill shortcut in the interaction test; termination verification is a separate guarded test.
2. Start `node dist/cli.js` with native terminal input/output and fixed dimensions. Verify `stdin.isTTY`, raw-mode capability, interactive TUI header and actual rendered frames, so the non-TTY table fallback cannot masquerade as a TUI pass.
3. Select one owned row with arrow input. Trigger manual refresh with `r`; wait for at least two automatic refresh opportunities. Insert/remove another owned row and change sorting with `s`. Confirm selection remains on the same PID/port when it remains visible, using the terminal frame and selected action target as evidence. Handle variable native discovery latency with bounded condition waits, not exact sleep timing assertions.
4. Drive `e` and `o` and capture arguments through harmless launchers/stubs. Use a temporary project path containing spaces. On Unix intercept only the selected launcher command while native discovery stays real. On Windows either use harmless configured editor executables or a documented test-only runner boundary around browser Start-Process. Do not open real applications or shadow the entire PowerShell executable and thereby replace native discovery. A stubbed launch is allowed by section 7.3; identify it clearly.
5. Verify the launcher receives the expected directory/URL and inherited locale/environment, preserving argument boundaries. Retain the existing foreground-editor lifetime regression; do not wait for an indefinitely running editor before continuing the terminal test.
6. Send `q`, assert normal CLI exit, and verify terminal settings are restored. Record session input, output frames, exit status, dimensions, terminal host/version and any intercepted command arguments. Keep timeouts and cleanup restricted to owned resources.

These are proposed native terminal tests, not existing results. A functional PTY/ConPTY session is an actual OS terminal interface; an Ink component renderer with synthetic input is not. The release reviewer must confirm this evidence satisfies the specification's "real terminal" wording before closing RV-04 from CI. If human-observed desktop-terminal behavior is required, hosted CI alone does not close that interpretation of the gate.

### C. Final matrix and artifact review

After necessary test-only additions, run all four jobs against one identified final candidate. Inspect every step, test totals/skips, actual native captures and terminal transcripts. Independently check that terminal jobs did not fall back to noninteractive output and that launcher interception did not turn native discovery into a fixture test. A green upload step or configured workflow is insufficient. Avoid product-code changes unless a reproducible defect requires the smallest correction and its regression test.

## Manual: Ubuntu Studio checks

These checks can be performed locally without Mac/Windows hardware. The assistant can drive a native Ubuntu terminal/PTY and record behavior; human inspection of the desktop terminal's visible appearance requires the user's observation if desktop access is unavailable to the assistant.

| Local check | Procedure | Required evidence |
| --- | --- | --- |
| Environment | Record Ubuntu Studio release, kernel, terminal application/version, Node, lsof, locale and candidate SHA | Environment record with commands/output |
| Native listener behavior | Run table/JSON/check against the owned loopback fixture; repeat the existing guarded stop/free-port/sentinel checks | Exact owned PID/port, command results and guard outcomes |
| TUI lifecycle | Open the built CLI in a terminal, navigate to an owned row, press r, wait for automatic refresh, add/remove a different owned fixture, change sort, confirm selection stays with its PID/port, then q | Session transcript; selected identity before/after; exit and restored keyboard/echo behavior |
| Editor shortcut | Set a per-session harmless editor command whose executable/project path contains spaces, press e on the owned row, inspect argument/locale log | Captured directory and intact arguments; no real editor launched |
| Browser shortcut | Intercept only the browser launcher using a harmless per-session stub; press o on the owned row | Captured localhost URL; no real browser launched |
| Human presentation check | Inspect readable rows/highlight, keyboard response, refresh behavior and exit in the normal Ubuntu Studio terminal | Named tester, terminal/version, date, observations/screenshots if available |

Use only temporary owned fixtures, one-session environment overrides and dedicated evidence directories. Do not stop other listeners, use broad process-name killing, or change persistent desktop defaults. If a target cannot be authenticated, stop the check without signalling. The current signal guard and ownership regression tests must remain intact.

Ubuntu Studio results close Linux gaps only. They do not establish Windows PowerShell or macOS terminal behavior. Existing backend fixtures and the earlier native macOS/Windows records remain separate evidence.

## Execution order and final decision

1. Preserve the baseline specification/reports/artifacts and identify the final candidate. Keep all evidence generated after the implementation commit clearly associated with the SHA actually tested.
2. Complete Ubuntu Studio native terminal and harmless shortcut checks; record any unavailable human desktop observation separately.
3. Add only test/CI evidence capture and native terminal harness work needed for RV-04/RV-05/RV-07. Qualify Unix PTY and Windows ConPTY before treating either as acceptance evidence.
4. Resolve RV-03's existing evidence boundary explicitly; do not weaken the process-ownership safeguard.
5. Run the complete four-job matrix and inspect fresh native/terminal artifacts. If functional terminal evidence is insufficient or unavailable on a platform, obtain remote/tester access or leave the gate pending.
6. Produce a final checklist marking RV-01 through RV-07 PASS, FAIL or PENDING, with SHA, OS/runtime/tool versions, commands, native-versus-fixture classification, run/job/artifact identifiers and transcript/manual-record links.

AC-12 can pass only when every mandatory section 7.3 outcome has satisfactory recorded evidence and all required automated checks pass. Planned automation, absent hardware, or an unapproved interpretation of "real terminal" cannot count as a pass. If required access remains unavailable, the decision is **release acceptance pending**, with the precise missing check identified. This plan does not waive the authoritative specification or authorize merging, tagging or publishing v2.0.1.
